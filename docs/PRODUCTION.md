# KIXO: production-сборка и эксплуатация

Подготовлен production runtime с демонстрационным каталогом. Домен/хостинг,
реквизиты реального магазина и настоящий ассортимент пока не предоставлены.
В demo-режиме заказы действительно сохраняются, но **не означают реальную продажу
или доставку**. Выручка от демо-заказов не учитывается в бизнес-показателях.

## Проверка перед выпуском

```bash
npm ci
npm run db:generate
npm run lint
npm run typecheck
npm run test
npm run build
npm run test:e2e
npm run release:check
```

Тесты намеренно отказываются использовать рабочий `DATABASE_URL`. Для них нужен
локальный `TEST_DATABASE_URL` и имя базы, заканчивающееся `_test`:

```bash
cp .env.test.example .env.test.local
docker compose -f docker-compose.test.yml up -d
npm run test:db:migrate
npm run test:db:seed
npm run test
npm run build
npm run test:e2e
```

Playwright запускает **production standalone**, а не dev-сервер, на отдельном
порту 3100. Он не переиспользует уже запущенный сервер. Браузерные traces выключены,
чтобы не сохранять формы/сессионные данные. GitHub Actions повторяет этот процесс
на собственной временной PostgreSQL и не получает секреты Supabase.

`npm run release:check:local` проверяет локальный production-запуск.
`npm run release:check` требует настоящий HTTPS-домен. Пока домен не выбран,
эта проверка ожидаемо сообщает, что публичная конфигурация не завершена.

## Конфигурация

Образец — `.env.production.example`. Секреты передавайте средствами хостинга,
secret manager либо приватным `.env.production` на сервере с правами `600`.
Не копируйте `.env` в публичные артефакты или Docker-образ.

- `DATABASE_URL`: Supabase Session pooler 5432, TLS обязателен.
- `NEXTAUTH_URL`, `NEXT_PUBLIC_SITE_URL`: один origin с HTTPS.
- `NEXTAUTH_SECRET`: отдельный случайный секрет, минимум 32 символа.
- `APP_MODE=demo`, `NEXT_PUBLIC_STORE_MODE=demo`: текущий режим.
- `TRUST_PROXY=true`: только за доверенным ingress, который перезаписывает
  `X-Forwarded-For`. В противном случае оставьте `false`; лимит будет общим.
- `S3_*`: нужны для загрузки изображений. При отсутствии S3 администратор может
  добавлять изображения из `public/images/` и разрешённого Unsplash.

`NEXT_PUBLIC_*` фиксируются при сборке. Меняя домен, публичный режим или S3/CDN host,
пересоберите приложение. Внутренний сервер должен быть закрыт от прямого доступа;
наружу выставляйте HTTPS через reverse proxy/managed hosting.

## Строгая проверка сертификата Supabase

Текущий локальный demo использует TLS `sslmode=require`. Отдельная проверка
`sslaccept=strict` без CA завершилась ошибкой self-signed certificate in chain.
Этот режим шифрования нельзя выдавать за проверку подлинности сервера.

Перед публичным запуском скачайте CA **из Supabase Dashboard → Database Settings →
SSL Configuration**. Не используйте сертификат, просто полученный по той же
непроверенной сетевой цепочке. Для Prisma 6 установите `sslaccept=strict` и `sslcert`
в `DATABASE_URL`, затем подтвердите подключение через `npm run db:check` и readiness.

Для Docker поместите публичный CA в `certs/supabase-ca.pem`: Compose монтирует папку
read-only в `/app/certs`, а `.env.production.example` использует этот абсолютный путь.
Для запуска непосредственно на Node.js задайте абсолютный путь своего сервера.
В `certs/` не должно быть приватных ключей. Сертификат не предоставлен пользователем;
его строгая проверка остаётся блокером публичного запуска. `release:check` проверяет
наличие обязательного режима `sslaccept=strict` для удалённой production-БД.

Официальные настройки: [Supabase SSL](https://supabase.com/docs/guides/platform/ssl-enforcement),
[Prisma 6 TLS](https://docs.prisma.io/docs/orm/v6/overview/databases/postgresql).

## Запуск без Docker

```bash
npm run db:migrate
npm run build
npm run start -- --port 3001
```

`start` запускает `.next/standalone/server.js`. Сборка копирует статические файлы и
`public`, удаляет `.env*` из standalone и проверяет выходные файлы на попадание
секретов. Производственный runtime не зависит от dev-сервера Next.js.

## Docker

```bash
# Сначала заполните .env.production настоящим доменом и секретами.
docker compose --env-file .env.production -f docker-compose.production.yml build
# Миграции выполняются отдельно из исходного checkout с теми же секретами.
npm run db:migrate
docker compose --env-file .env.production -f docker-compose.production.yml up -d
```

В Dockerfile есть отдельная цель `migrate` для CI/release job, если миграции нужны
без Node.js на хосте. Запускайте её с секретами как runtime environment, а не
build arguments. В build stage production-база не нужна. Runtime работает от
непривилегированного пользователя `node`; Compose публикует порт только на loopback.

Docker engine в текущей среде отсутствует: Docker build здесь не выполнялся.
Тот же standalone runtime проверяется локально и браузером; перед выбором Docker
на сервере следует выполнить сборку образа на целевой платформе.

## Проверка после выкладки

```bash
curl --fail https://YOUR-DOMAIN/api/health
curl --fail 'https://YOUR-DOMAIN/api/health?ready=1'
npm run db:check
```

Первая проверка подтверждает работу сервера; `ready=1` также проверяет PostgreSQL.
Health API не раскрывает строку подключения, пароли или содержимое базы.
Настройте внешний uptime monitor на этот URL и сбор серверных журналов хостинга.
Не включайте запись тел заказов, паролей или cookies в логи.

## Заказы и остатки

Сервер повторно рассчитывает цены/скидки/доставку и сравнивает итог с подтверждённой
покупателем суммой. Изменение цены возвращает HTTP 409: интерфейс обновляет quote
и требует повторного подтверждения. Ключ идемпотентности связан с содержимым
запроса и пользователем; повтор того же запроса не создаёт второй заказ.
Остатки изменяются в Serializable-транзакциях с повтором при конфликте.

Админка проверяет роль на сервере при каждом действии. Редактирование остатка
проверяет, что он не изменился с момента открытия формы. Отмена возвращает
остаток один раз. Наличная оплата становится `PAID` при доставке.
В demo-режиме все заказы маркируются `demo=true`.

## Резервное копирование и проверка восстановления

```bash
npm run db:backup -- artifacts/kixo-private-YYYYMMDD.dump
```

Копируется только public-схема магазина. Каталог `artifacts/` исключён из Git и
Docker, файл создаётся с правами `600` без перезаписи существующей копии.
Копия содержит пользовательские данные и хеши паролей; храните её зашифрованной
во внешнем приватном хранилище. Настройте регулярное расписание на хостинге.
Объекты S3 и служебные схемы Supabase в эту копию не входят.

Проверка восстановления разрешена только в пустую **локальную** базу:

```bash
createdb kixo_verify_restore_test
RESTORE_DATABASE_URL='postgresql://USER:PASSWORD@127.0.0.1:5432/kixo_verify_restore_test' \
  npm run db:restore:test -- artifacts/kixo-private-YYYYMMDD.dump
```

Инструмент не очищает существующие базы. При проверке совместимости с обычным
PostgreSQL удаляются только встречающиеся в дампе Supabase настройки колонок
`pg_attver`; прикладная схема, данные и ограничения восстанавливаются в отдельных
pre-data/data/post-data фазах. Восстановление на рабочий Supabase — отдельная
операторская операция, не выполняемая этой командой автоматически.

## Переход к реальным продажам

Текущий релиз предназначен для демонстрации. Для реальных продаж владелец должен
предоставить и проверить ассортимент, фотографии именно этих моделей, цены и
фактические остатки, контакты, юридические сведения и условия обслуживания.
Установите `demo=false` только у проверенных реальных товаров. В live-режиме
checkout отклоняет демонстрационные позиции; demo seed также запрещён.

После настройки бизнес-процессов смените оба параметра режима на `live`, задайте
контакты и пересоберите приложение. Справочные тексты нужно адаптировать под
фактические условия магазина. Click/Payme не подключены и не имитируют оплату;
для них нужны официальные проверенные адаптеры и merchant credentials.
Рассылка, SMS, автоматическая доставка и возврат денег через платёжный провайдер
пока не реализованы. Наличный checkout технически проверен.

## Обновление и откат

Сначала резервная копия, затем аддитивные миграции, staging-проверка и переключение
трафика на проверенную сборку. Храните предыдущий container image/build для отката
приложения. Не запускайте `prisma migrate reset`, `db push --accept-data-loss` или
автоматический обратный SQL на рабочей Supabase. При изменении схемы совместимость
со старой сборкой проверяйте до переключения трафика.
